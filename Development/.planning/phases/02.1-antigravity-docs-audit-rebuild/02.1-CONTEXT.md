# Phase 02.1: Antigravity Docs Audit & Rebuild - Context

**Gathered:** 2026-02-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Map and audit all Antigravity-related documentation, replace or delete obsolete guidance, and rebuild documentation assumptions based on current system behavior. This phase is documentation-focused and does not add new product capabilities.

</domain>

<decisions>
## Implementation Decisions

### Audit scope
- In-scope sources: all markdown across the repo, including `Development/docs/**` and root-level READMEs/checklists.
- Detect legacy content via explicit Antigravity terms and any onboarding/deployment/config docs that contradict the current stack.
- Scan non-markdown text sources: `.md`, `.txt`, and comments in code.
- Update/remove anything that conflicts with the current stack, even if not explicitly Antigravity-related.

### GSD folders
- Exclude `.claude/`, `.opencode/`, and `.gemini/` directories from audit scope; do not change any files under these folders.
- List `.gemini/` in the inventory as "Out of Scope — GSD required" with scope labeled "GSD tooling".
- Treat any `.gemini`-named docs outside the `.gemini/` folder as in-scope Antigravity docs.

### Rebuild baseline
- Source of truth is the combination of codebase behavior, Supabase schema/migrations, and ROADMAP/PROJECT decisions.
- Conflicts: use judgment; when unsure, flag for review rather than asserting a single source.
- Include current-status notes in updated docs (implemented vs planned).

### Output structure
- Deliverables include: updated docs, inventory list of reviewed files, deprecated list, and a summary report of changes.
- Include a checklist of fixes applied vs pending in both the summary report and the inventory list.

### Claude's Discretion
- Where to store inventory/deprecated/summary artifacts (docs folder vs planning folder).
- How to mark deprecated content (remove vs label vs move to legacy section).
- How to resolve ambiguous conflicts when sources disagree.

</decisions>
