## Summary

This research covers how to plan a doc audit that removes legacy Antigravity guidance and rebuilds documentation to reflect the current system. The audit must scan all Markdown plus `.txt` and code comments, then reconcile doc claims against the codebase, Supabase schema/migrations, and ROADMAP/PROJECT decisions. The repo has two product variants (static and full), and documentation scope must clearly separate them.

The current stack is Next.js 15 + React 19 + Supabase + Resend, with legacy Firebase/Zoho artifacts still present. Documentation should be treated as a living system snapshot: every updated section needs a current-status note (implemented vs planned) and a source-of-truth reference. Conflicts should be flagged instead of guessed, with a dedicated “needs review” section in the summary and inventory.

**Primary recommendation:** Create a dedicated audit bundle under `Development/docs/audits/antigravity-2026-02/` (inventory, deprecated list, summary) and update core docs using code/migrations as the authoritative baseline, flagging unresolved conflicts explicitly.

## Architecture Patterns

### Recommended Project Structure
```
Development/
├── docs/
│   ├── README.md                 # Doc index + scope
│   ├── ...                       # Core system docs
│   └── audits/
│       └── antigravity-2026-02/
│           ├── INVENTORY.md      # Reviewed files + checklist
│           ├── DEPRECATED.md     # Removed/moved sections/files
│           └── SUMMARY.md        # Change log + pending items
└── ...
```

### Pattern 1: Documentation Inventory Table
**What:** Single source list of all reviewed files with status and checklist.
**When to use:** Start of audit and updated as each file is reviewed.
**Example:**
```markdown
<!-- Source: Development/docs/README.md + audit decisions in .planning/phases/02.1-antigravity-docs-audit-rebuild/02.1-CONTEXT.md -->
| File | Scope | Status | Findings | Fixes Applied | Pending |
|------|-------|--------|----------|---------------|---------|
| Development/docs/README.md | Full version | Updated | Legacy Antigravity note verified | ✔ Scope note aligned | ☐ Verify env var list vs code |
```

### Pattern 2: Status Notes in Docs
**What:** Explicit “Implemented vs Planned” note for any feature or flow.
**When to use:** Any section describing user flows, APIs, or database fields.
**Example:**
```markdown
**Status:** Implemented (Phase 1 complete); Wizard unification planned in Phase 2.
```

### Pattern 3: Conflict Flagging
**What:** Mark conflicts instead of deciding when sources disagree.
**When to use:** Supabase schema vs docs, or ROADMAP vs code behavior.
**Example:**
```markdown
> ⚠️ **Needs Review:** Docs list `documents.deleted_at`, but schema in migrations must confirm current column names.
```

### Anti-Patterns to Avoid
- **Assuming doc truth:** Treat docs as output; verify against code + migrations.
- **Static/full version mix-ups:** Never apply full-version docs to `website static view dev/` unless explicitly shared (branding only).
- **Silent conflict resolution:** If sources disagree, flag it rather than guessing.

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Schema documentation | Manual table lists only from docs | Supabase migrations in `supabase/migrations/` | Migrations are canonical and reflect actual schema |
| Status lists | Rewriting status flow from memory | State machine definitions in code (`lib/state-machines/`) | Prevents stale or incomplete status sets |
| Env var lists | Copying from old docs | Current `.env.example` + code references | Avoids mismatch with runtime usage |

**Key insight:** Documentation should be derived from authoritative sources (code + migrations + roadmap), not rewritten from legacy notes.

## Common Pitfalls

### Pitfall 1: Missing Non-Markdown Sources
**What goes wrong:** Legacy guidance persists in `.txt` files or code comments.
**Why it happens:** Audit focuses only on Markdown docs.
**How to avoid:** Scan `.md`, `.txt`, and comments with keyword searches (Antigravity, Firebase, Firestore, Zoho, Cloud Functions).
**Warning signs:** “No matches found” for Antigravity, but Firebase/Zoho references still exist.

### Pitfall 2: Confusing Full vs Static Version
**What goes wrong:** Docs are updated with assumptions that apply only to the full app, but shared with static version.
**Why it happens:** Root README and `Development/docs/README.md` already split scope, but edits ignore it.
**How to avoid:** Keep scope banners at top of docs; isolate shared branding only.
**Warning signs:** References to auth or portals appear in static-site docs.

### Pitfall 3: Migrated Stack Mismatch
**What goes wrong:** Docs still describe Firebase/Zoho or Cloud Functions workflows.
**Why it happens:** Legacy integrations remain in the repo even after migration.
**How to avoid:** Treat Supabase + Resend as the current baseline and flag any remaining Firebase references as deprecated or legacy.
**Warning signs:** Docs mention Firestore triggers or Firebase functions config.
